# 7월 25일 필기 — CURSOR AI 정리 (개념 + 사용 가이드)

## 핵심요약

**CURSOR AI**는 코드 자동완성 도구가 아니라 **개발 환경 안에서 실제로 일하는 팀원처럼 동작하도록 설계된 AI 기반 IDE**다. 핵심은 "코드 생성"이 아니라 프로젝트 파일 시스템·Git 저장소·데이터베이스 구조·외부 컨텍스트(MCP 서버)까지 AI가 직접 인식하고 활용한다는 점 — 즉 AI에게 코드 조각이 아니라 **개발 환경 전체를 연결해주는 도구**다. 기본 사용 방식은 세 갈래로 나뉜다: 단일 질문·설명·간단 수정을 다루는 **Chat 모드**, 선택 범위만 즉시 고치는 **Inline Edit**, 그리고 "목표 분석 → 파일 탐색 → 수정/생성 → 요약 → 커밋"까지 다단계 작업을 자동 처리하는 **Agent 모드**(가장 강력한 기능). 이 Agent 모드가 실제로 신뢰할 수 있게 동작하려면 **MCP(Model Context Protocol)** 연동이 필수인데, FILESYSTEM MCP(실제 파일 읽기/수정)·DATABASE MCP(스키마·데이터 확인)·GIT MCP(커밋·브랜치·diff)·CUSTOM CONTEXT MCP(규칙·문서 근거)를 통해 AI가 "기억이나 추측"이 아니라 **실제 리소스를 기준으로 판단**하게 만든다. 이 구조 위에 **README(프로젝트 규칙의 원문, SSOT)**와 **.cursorrules(AI 행동 헌법 — MCP 우선 사용 강제, 추측 금지, 출력 형식 통제)**가 얹히면 "법전 + 집행 규칙"이 완성되고, 이때 비로소 Cursor는 단순 보조가 아니라 실제 프로젝트 팀원 수준으로 동작한다. 토큰 관점에서도 이점이 있다 — 파일 전체를 매번 프롬프트에 밀어넣지 않고 필요한 파일만 search 기반으로 선택적으로 읽기 때문에 재요청·재수정이 줄고 토큰 낭비가 감소한다. 다만 주의사항도 명확하다: MCP 없이 Agent 모드를 남용하지 않기, 운영 DB 직접 연결 지양, `node_modules`·빌드 결과물은 컨텍스트에서 제외, 규칙 없는 대형 프로젝트에서의 사용 지양. 한 문장으로 요약하면 — **규칙(.cursorrules)과 컨텍스트(MCP)를 갖춘 순간, Cursor AI는 코드를 설명해주는 도구에서 실제로 일하는 개발 파트너가 된다.**

---

## CURSOR AI란 무엇인가

CURSOR AI는 AI를 단순한 코드 자동완성 도구가 아니라 개발 환경 안에서 실제로 일하는 팀원처럼 사용하도록 설계된 AI 기반 IDE다. Cursor의 핵심은 "코드 생성"이 아니라 다음 개발 자원을 AI가 직접 인식하고 활용한다는 점이다: 프로젝트 파일 시스템, Git 저장소와 변경 이력, 데이터베이스 구조, 외부 컨텍스트(MCP 서버). 즉, Cursor는 AI에게 코드 일부가 아니라 **개발 환경 전체를 연결해주는 도구**다.

### 핵심 특징

| 특징 | 설명 |
|---|---|
| 코드베이스 인식 | 프로젝트 전체 파일 구조 인식 · 여러 파일 간 의존 관계 파악 · 실제 파일 기준 판단 · 추측 기반 응답 최소화 |
| Agent 모드 | 작업 목표 분석 → 필요한 파일/리소스 탐색 → 파일 수정·생성 → 변경 결과 요약 → 필요 시 커밋까지 수행. 여러 단계 작업을 한 번에 자동 처리 |
| MCP 연동 | AI에게 사실 기반 컨텍스트 제공 — 기억·추측이 아닌 실제 리소스를 기준으로 판단 |

### 기본 사용 방식

| 모드 | 특징 | 적합한 상황 |
|---|---|---|
| Chat 모드 | 단일 질문/응답, 코드 설명, 개념 학습, 간단한 수정 제안 | 빠른 질의응답 |
| Inline Edit | 선택한 코드 범위를 직접 수정 | 단일 파일 작업, 빠른 리팩토링 |
| Agent 모드 | 다단계 작업 자동 수행, 여러 파일 수정, MCP 서버 적극 활용 | 중·대형 작업 (필수적) |

### 규칙 시스템 — README와 .cursorrules

| 구성 | 역할 | 비유 |
|---|---|---|
| README | 프로젝트 규칙의 원문 · 아키텍처 기준 · 디렉토리 구조 규칙 · API 사용 원칙. 프로젝트의 단일 진실(SSOT) | 법전 |
| .cursorrules | AI 행동 헌법 · MCP 우선 사용 강제 · 추측 금지 · 출력 형식 통제 | 집행 규칙 |

### Cursor AI + MCP 조합

| 구성 요소 | 역할 |
|---|---|
| README | 규칙과 기준 |
| .cursorrules | AI 행동 통제 |
| Custom Context MCP | 규칙·문서 근거 |
| Filesystem MCP | 실제 코드 수정 |
| Database MCP | DB 사실 확인 |
| Git MCP | 변경 이력 관리 |

이 조합이 완성되면 AI는 단순 조수가 아니라 실제 프로젝트 팀원 수준으로 동작한다.

> **토큰 관점 장점**: 파일 전체를 매번 프롬프트에 넣지 않고 필요한 파일만 선택적으로 읽으며, search 기반으로 정확히 접근하기 때문에 재요청·재수정이 줄고 결과적으로 토큰 낭비가 줄어든다.

> **주의사항**: MCP 없이 Agent 모드 남용 금지 · 운영 DB 직접 연결 지양 · `node_modules`, 빌드 결과물은 컨텍스트에서 제외 · 규칙 없는 대형 프로젝트 사용 지양. Cursor는 규칙과 컨텍스트가 있을 때 가장 강력하다.

### 추천 초기 세팅 순서

1. Cursor 설치
2. Git 저장소 열기
3. README 정비
4. `.cursorrules` 작성
5. MCP 서버 설정 (Filesystem → Custom Context → 필요 시 Database, Git)
6. Agent 모드 테스트

### 적합한 대상

실무 개발자 · 교육/강의 프로젝트 운영자 · 자동화·리팩토링이 잦은 환경 · 대형 코드베이스 관리자 · AI를 팀원처럼 활용하고 싶은 사용자

## 25일 핵심 정리

### 1) 기본 대화 · 코드 보조 기능 — Chat

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 일반 질의응답 | 코드, 개념, 오류 원인 설명 | 특정 함수 역할 설명 |
| 코드 설명 | 선택한 코드의 동작 방식 설명 | 레거시 코드 분석 |
| 코드 생성 | 요구사항 기반 코드 생성 | 컴포넌트 초안 생성 |
| 리팩토링 제안 | 가독성·성능 개선 제안 | 함수 구조 개선 |
| 에러 분석 | 컴파일/런타임 오류 원인 분석 | 에러 로그 해석 |

가장 기본적인 층위 — 파일을 직접 고치지 않고 설명·제안만 오가는 단계.

### 2) Inline Edit — 파일 이동 없이 즉시 수정

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 코드 직접 수정 | 선택한 코드 범위 즉시 수정 | 함수 로직 변경 |
| 부분 리팩토링 | 특정 블록만 개선 | 조건문 정리 |
| 스타일 통일 | 포맷·컨벤션 정리 | 코드 스타일 통일 |
| 빠른 수정 | 파일 이동 없이 수정 | 변수명 변경 |

Chat이 "설명"에 머문다면 Inline Edit은 선택 범위를 실제로 바꾸는 첫 단계 — 다만 단일 파일 범위로 한정된다.

### 3) Agent 모드 — 자동화의 핵심

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 다단계 작업 수행 | 여러 작업을 연속 처리 | 분석 → 수정 → 요약 |
| 파일 탐색 | 필요한 파일 자동 탐색 | 관련 코드 찾기 |
| 코드 수정 | 여러 파일 동시 수정 | 전역 리팩토링 |
| 작업 계획 수립 | 목표 기반 작업 순서 결정 | 기능 추가 플로우 |
| 결과 요약 | 변경 사항 요약 제공 | PR 요약 |

Inline Edit이 "선택 범위 하나"라면 Agent 모드는 "여러 파일에 걸친 목표"를 처리한다는 점이 결정적 차이 — 단, 뒤따르는 MCP 연동 없이는 추측 기반 수정에 그칠 위험이 있다.

### 4) Filesystem MCP — Agent가 실제 파일을 다루게 하는 기반

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 파일 목록 조회 | 실제 디렉토리 구조 확인 | 프로젝트 구조 파악 |
| 파일 읽기 | 실제 파일 내용 로드 | 코드 분석 |
| 파일 생성 | 새 파일 생성 | 컴포넌트 생성 |
| 파일 수정 | 기존 파일 변경 | 코드 자동 반영 |
| 검색 | 파일/내용 탐색 | 특정 함수 위치 찾기 |

Agent 모드가 "계획"을 세운다면 Filesystem MCP는 그 계획을 실제 파일 시스템에 반영하는 손발 역할.

### 5) Custom Context MCP — 규칙 문서를 근거로 판단하게 함

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 규칙 제공 | README, 규칙 문서 컨텍스트 | 아키텍처 준수 |
| 문서 기반 판단 | 추측 제거 | 규칙 위반 방지 |
| search_context | 전체 문서 텍스트 검색 | 키워드 탐색 |
| get_context_info | 컨텍스트 메타 정보 | 경로/상태 확인 |

README·`.cursorrules`가 "규칙"이라면 Custom Context MCP는 그 규칙을 AI가 실시간으로 조회할 수 있게 만드는 연결고리.

### 6) Database MCP — DB를 추측하지 않고 확인

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 스키마 조회 | 테이블/컬럼 구조 확인 | Entity 설계 |
| 컬럼 검증 | 컬럼 존재 여부 확인 | SQL 오류 방지 |
| 데이터 확인 | 실제 데이터 존재 확인 | 버그 분석 |
| 관계 추론 | FK 구조 파악 보조 | JOIN 설계 |
| 읽기 기반 분석 | DB 상태 기반 판단 | 조건 분기 검증 |

운영 DB에 직접 연결하지 않고도(주의사항 참고) 스키마·데이터 사실을 근거로 코드를 판단하게 하는 것이 핵심.

### 7) Git MCP — 변경 이력을 사실 기반으로 관리

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 상태 확인 | 수정/추가 파일 확인 | 작업 전 점검 |
| 커밋 로그 조회 | 변경 이력 확인 | 원인 추적 |
| diff 분석 | 코드 변경 비교 | 영향도 분석 |
| 브랜치 생성 | 안전한 작업 분리 | 기능 개발 |
| 커밋 수행 | 변경 사항 기록 | Agent 자동 커밋 |

Agent 모드의 마지막 단계("필요 시 커밋까지 수행")를 실제로 수행하는 실행부.

### 8) 규칙 · 통제 기능 (.cursorrules)

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 행동 통제 | AI 행동 규칙 정의 | 추측 금지 |
| MCP 우선 사용 | 리소스 강제 사용 | 파일 직접 접근 방지 |
| 출력 형식 통제 | 결과 포맷 고정 | 보고서 스타일 |
| 보안 경계 | 접근 범위 제한 | 경로 보호 |

Agent + 모든 MCP가 갖춰져도 `.cursorrules`가 없으면 "언제 MCP를 써야 하는지"를 AI가 임의로 판단하게 된다 — 그래서 이 문서는 이를 "AI 행동 헌법"이라 부른다.

### 9) 생산성 · 품질 향상 기능

| 기능 | 설명 | 활용 예시 |
|---|---|---|
| 토큰 절약 | 불필요한 재요청 감소 | 반복 작업 제거 |
| 정확도 향상 | 사실 기반 판단 | 오류 감소 |
| 자동화 | 반복 작업 자동 처리 | 리팩토링 |
| 교육 활용 | 규칙 기반 과제 검증 | 수업/과제 |

Chat·Inline Edit·Agent·MCP·규칙 다섯 계층이 모두 맞물렸을 때 나오는 결과물 — 이 문서의 결론이자 8번 항목(규칙)이 왜 필요한지에 대한 답이기도 하다.

### 10) 전체 구조 한 줄 요약

CURSOR AI는 **Chat + Agent + MCP + 규칙(.cursorrules)**을 결합하여 AI를 단순 보조가 아닌 실제 개발 팀원으로 만드는 IDE다. README가 규칙의 원문(SSOT)을 쥐고, `.cursorrules`가 그 규칙의 집행을 강제하며, MCP 네 종류(Filesystem·Custom Context·Database·Git)가 "추측 대신 사실"을 공급하는 구조 — 이 네 layer가 모두 갖춰졌을 때 Agent 모드가 비로소 신뢰할 수 있는 다단계 자동화로 동작한다.
