# 7월 28일 필기 — Cursor 룰셋 실습 가이드 (컨텍스트 엔지니어링 · 하네스 엔지니어링)

## 핵심요약

`02/` 폴더를 대상으로 **"AI에게 우리 팀 규칙을 지키게 만들기"** 10단계 실습을 진행했다. 출발점은 관찰이었다 — 아무 준비 없이 Cursor에게 "상품 카드 컴포넌트 만들어줘"라고 시키면(1단계) 색·파일 위치·확장자·금액 포맷이 사람마다 제각각으로 나온다. 원인은 단순하다: 팀 디자인 가이드(`02/DOCS/DESIGN/2026_UIUX_디자인가이드.md`)가 폴더에 존재해도 **AI는 그 문서를 읽지 않는다** — 보여주지 않으면 모른다. 이 관찰에서 두 용어가 갈라진다. **컨텍스트 엔지니어링**(AI가 무엇을 보게 할지 정하는 일)과 **하네스 엔지니어링**(AI가 무엇을 하고 무엇을 못 하게 할지 정하는 일). 2단계에서 `@문서`로 근거를 직접 붙이면 결과가 즉시 좋아지지만, 매 요청마다 긴 문장을 타이핑할 수 없으므로 3~5단계에서 **규칙 파일(`.mdc`)**을 넓은 범위 → 좁은 범위 순으로 쌓는다: 전역 규칙(`alwaysApply: true`, 프로젝트 전체 — 보안·Git·작업 원칙처럼 항상 지켜야 하는 것만 짧게), `02/` 규칙(`globs: 02/**`, 항상은 아니고 조건부), `02/FN/` 규칙(`globs: 02/FN/**`, 디자인 토큰·CTA 개수·금액 포맷 같은 프론트 세부 규칙). 여기서 가장 흔한 오해가 나온다 — `globs`는 문서를 자동으로 읽어오는 게 아니라 **규칙을 켜는 스위치일 뿐**이고, 문서를 읽게 하려면 규칙 본문에 "이 문서를 확인한다"라고 직접 적어야 한다. 6단계에서 `@` 없이 같은 요청을 다시 던져 규칙이 실제로 먹는지 확인한 뒤, 3부(7~10단계)는 범위와 안전을 다룬다: 7단계는 FN 전용 규칙을 일부러 `alwaysApply: true`로 바꿔 백엔드(Java) 작업에까지 프론트 디자인 규칙이 끼어드는 오작동을 관찰하고 원상복구하는 실험, 8단계는 같은 패턴으로 BN(Spring) 규칙을 추가, 9단계는 `.cursorignore`로 `.env` 등 민감 파일 자체를 못 보게 차단, 10단계는 세 군데(`​.cursor`, `02/FN/.cursor`, `02/BN/.cursor`)에 흩어진 규칙을 `feature/lab-내이름` 브랜치로 커밋해 `dev`로 PR을 올리는 것 — **Project Rules는 저장소 안 파일이라 git으로 팀 전체에 공유되지만, User Rules는 개인 설정이라 공유되지 않는다**는 것이 이 단계의 핵심 포인트. 마지막으로 규칙에는 네 가지 타입(Always·Auto Attached·globs·Agent Requested·description만·Manual·셋 다 비움)이 있고, 오늘 실습은 그중 Always와 Auto Attached만 다뤘다.

## 0부 — 준비: 내 브랜치 만들기

| 단계 | 명령 | 비고 |
|---|---|---|
| 0-1 | `git checkout dev` → `git pull origin dev` | dev를 최신으로 |
| 0-2 | `git checkout -b feature/lab-내이름` | **반드시 dev에서 분기** — main에서 만들면 안 됨 |
| 0-3 | `git branch` | `*` 표시가 내 브랜치에 있는지 확인 |
| 0-4 | Cursor 오른쪽 채팅창(Agent 모드) 열어두기 | 이후 모든 실습의 입력창 |

## 1부 — 컨텍스트: AI가 보는 것

### 1단계 — 그냥 시켜보기

```
02/FN에 상품 카드 컴포넌트 하나 만들어줘
```

아무 준비 없이 요청 → 결과를 고치지 않고 그대로 관찰. 옆 사람과 비교할 항목: 주요 색, 파일 생성 위치, 확장자(`.jsx`/`.js`), 금액에 콤마(`1,000`) 유무.

**직접 열어서 대조**: `02/DOCS/DESIGN/2026_UIUX_디자인가이드.md`의 브랜드 색이 내가 받은 코드에 있었는지 확인.

> **결론**: AI는 그 문서를 읽지 않았다. 문서는 폴더에 그냥 있을 뿐 — 보여주지 않으면 AI는 모른다.

### 2단계 — @로 문서 붙이기

채팅창에 `@`를 치면 파일 목록이 뜨고, `2026_UIUX_디자인가이드.md`를 고르면 경로가 자동으로 들어간다.

```
@02/DOCS/DESIGN/2026_UIUX_디자인가이드.md 를 기준으로
02/FN/src/components/ProductTile.jsx 를 만들어줘.
색은 토큰(var(--color-*))만 쓰고, 금액은 toLocaleString('ko-KR') 써.
```

1단계 결과와 비교: 색이 가이드와 맞는지, 금액에 콤마가 붙었는지.

**배운 것**
- **컨텍스트 엔지니어링** = AI가 볼 것을 내가 정하는 일. `@`로 근거를 붙이면 결과가 달라진다.
- 문제: 이걸 매번 타이핑해야 하나? → 안 친다. 그래서 **규칙 파일**이 있다 (2부).

## 2부 — 규칙 만들기: 넓은 것 → 좁은 것

| 순서 | 규칙 | 적용 범위 |
|---|---|---|
| 3단계 | 전역 규칙 | 프로젝트 전체 |
| 4단계 | 02 규칙 | `02/` 폴더 |
| 5단계 | FN 규칙 | `02/FN/` 폴더 |

### 3단계 — 전역 규칙 만들기 (Always)

어디서 작업하든 무조건 지켜야 하는 것들. 루트에 `.cursor/rules/project-rules.mdc` 생성.

```yaml
---
description: 프로젝트 전역 최상위 규칙
alwaysApply: true
---
```

| 항목 | 뜻 |
|---|---|
| `description` | 이게 무슨 규칙인지 한 줄 설명 |
| `alwaysApply: true` | 항상 적용한다는 뜻 |

본문:

```markdown
# 프로젝트 전역 규칙

## 보안
- `.env`, API 키, 비밀번호를 코드·커밋에 넣지 않는다.

## Git
- `main`·`dev`에 직접 커밋하지 않는다. 기능 브랜치에서 작업한다.
- 기능 브랜치는 `dev`에서 분기하고, PR도 `dev`로 올린다.
- 커밋 메시지는 `<타입>(<범위>): <한국어 요약>` 형식.

## 작업 원칙
- 문서와 구현이 다르면 문서를 기준으로 맞춘다.
- 요청 범위 밖의 파일을 임의로 고치지 않는다.
```

저장 후 `지금 적용 중인 규칙이 뭐야?`로 확인.

> **중요**: Always 규칙은 짧게 쓴다. 모든 요청에 딸려 들어가므로 길게 쓰면 매번 그만큼 자리를 차지한다.

### 4단계 — 02 폴더 규칙 만들기 (globs)

`02/` 안에서 일할 때만 켜지는 규칙. `.cursor/rules/follow-02-docs.mdc` 생성.

```yaml
---
description: 02/ 작업 시 02/DOCS 문서를 우선 준수
globs: 02/**
alwaysApply: false
---
```

| 설정 | 뜻 |
|---|---|
| `globs: 02/**` | `02/` 아래 파일을 건드리면 켜진다 (`**`는 "그 아래 전부") |
| `alwaysApply: false` | 항상은 아니고, 위 조건일 때만 |

본문:

```markdown
# 02 작업 규칙

02/ 에서 작업할 때 아래 문서를 먼저 확인한다.
- `02/DOCS/02RULE.md`
- `02/DOCS/DESIGN/2026_UIUX_디자인가이드.md`

## 원칙
- 문서에 없는 새 관례를 만들면 문서에도 반영한다.
```

테스트: `02/FN에 버튼 컴포넌트 만들어줘`(켜져야 함) vs `01/FN에 버튼 컴포넌트 만들어줘`(꺼져야 함).

> **가장 헷갈리는 부분**: `globs: 02/**`라고 쓴다고 02 폴더의 문서를 AI가 다 읽어오는 게 아니다. **globs는 규칙을 켜는 스위치일 뿐** — 문서를 읽게 하려면 본문에 "이 문서를 확인한다"라고 직접 적어야 한다(4단계 본문에 문서 경로를 적은 이유).

### 5단계 — FN 규칙 만들기

범위를 한 번 더 좁힌다. 이번엔 규칙 파일을 그 폴더 안에 둔다: `02/FN/.cursor/rules/fn-design.mdc`.

> 규칙 파일은 폴더마다 둘 수 있다 — 루트에만 두는 게 아니다.

```yaml
---
description: FN 화면 구현 시 디자인 가이드 준수
globs: 02/FN/**
alwaysApply: false
---

# FN 디자인 규칙

화면·컴포넌트 작업 전 아래 문서를 먼저 읽는다.
- `02/DOCS/DESIGN/2026_UIUX_디자인가이드.md`
- `02/DOCS/DESIGN/시안_토큰.css`

## 필수
- 색은 `var(--color-*)` 토큰만. hex 하드코딩 금지.
- Primary CTA는 화면당 1개.
- 상품 타일은 보더리스. 카드 박스로 감싸지 않는다.
- 금액은 `toLocaleString('ko-KR')` + `원`.
- 클릭 요소는 `div` 금지 → `button` / `a`.
- 이미지에 `alt` = 상품명.
```

> **하지 말 것**: 디자인 가이드 내용을 규칙 파일에 통째로 복붙하지 않는다. 그 문서는 15KB가 넘고, 매 요청마다 그게 다 딸려 들어간다. 짧게 쓰고 경로만 가리킨다.

| 구분 | `.mdc` (규칙) | `.md` (문서) |
|---|---|---|
| 역할 | AI에게 주는 명령 | 그냥 자료 |
| 위치 | `.cursor/rules/` | 아무데나 |
| 자동 적용 | 된다 | 안 된다 |

### 6단계 — 규칙이 먹는지 확인하기

새 채팅을 열어(이전 대화 영향 배제) `@` 없이 1단계와 똑같은 문장을 다시 입력:

```
02/FN에 상품 카드 컴포넌트 하나 만들어줘
```

비교 항목: `@` 없이도 색이 맞는지, 금액에 콤마가 붙었는지, 클릭 요소가 `button`인지. 1단계·6단계 결과 스크린샷 두 장은 제출물이다.

**지금까지 만든 규칙**

| 파일 | 설정 | 범위 |
|---|---|---|
| `.cursor/rules/project-rules.mdc` | Always | 전체 |
| `.cursor/rules/follow-02-docs.mdc` | `02/**` | 02 전체 |
| `02/FN/.cursor/rules/fn-design.mdc` | `02/FN/**` | 프론트 |

> **핵심**: 넓은 규칙 위에 좁은 규칙이 겹쳐 쌓인다. FN 파일을 건드리면 셋이 동시에 켜진다.

## 3부 — 범위와 안전: 하네스

### 7단계 — Always는 왜 위험한가 (실험)

직접 망가뜨려 보고 원래대로 되돌린다.

1. `02/FN/.cursor/rules/fn-design.mdc`를 연다.
2. `globs:` 줄을 지우고 `alwaysApply: true`로 바꿔 저장.
3. 이번엔 **프론트가 아닌 백엔드** 작업을 시킨다: `02/BN에 상품 조회 API 하나 추가해줘`
4. 관찰: Java 작업인데 프론트 디자인 규칙이 끼어들었는지.
5. **반드시 원래대로 되돌린다**: `globs: 02/FN/**` 복원, `alwaysApply: false`로 재수정.

| 설정 | 언제 켜지나 | 이 규칙엔 |
|---|---|---|
| `alwaysApply: true` | 항상 | 과하다 |
| `globs: 02/FN/**` | FN 건드릴 때만 | 이게 맞다 |

### 8단계 — 백엔드 규칙 추가

`02/BN/.cursor/rules/bn-rules.mdc` 생성.

```yaml
---
description: BN(Spring) 코드 규칙
globs: 02/BN/**
alwaysApply: false
---

# BN 규칙
- Controller에 비즈니스 로직 금지. Service로 뺀다.
- 예외는 GlobalExceptionHandler에서 공통 처리.
- 시크릿은 application.yml에 직접 쓰지 않는다.
```

BN 작업을 시켜보고, 이번엔 FN 규칙이 끼어들지 않는지 확인.

### 9단계 — 못 보게 막기 (`.cursorignore`)

AI가 봐서는 안 되는 것(비밀번호 등)을 막는다. `02/FN/.cursorignore` 생성 — 문법은 `.gitignore`와 동일.

```
node_modules/
build/
.env
*.log
```

확인: `02/FN/.env 내용 보여줘` → 접근이 거절되는지.

> **Auto-run도 확인해두기**: Cursor 설정에서 AI가 명령을 스스로 실행하게 할 수 있다.

| 구분 | 예 |
|---|---|
| 자동 허용해도 됨 | 빌드 · 테스트 · 조회 (되돌리기 쉬움) |
| 매번 확인받아야 함 | 삭제 · git push · 배포 (되돌리기 어려움) |

### 10단계 — 커밋해서 조원과 공유하기

오늘 만든 규칙은 세 군데(`.cursor`, `02/FN/.cursor`, `02/BN/.cursor`)에 흩어져 있다. 모두 담는다.

```bash
git add .cursor 02/FN/.cursor 02/BN/.cursor 02/FN/.cursorignore
git status   # 무엇이 올라가는지, 시크릿이 섞이지 않았는지 반드시 확인
git commit -m "chore: Cursor 규칙 체계 추가 (전역·02·FN·BN)"
git push origin feature/lab-내이름
```

GitHub에서 PR을 올린다. **대상은 `dev`** — `main`이 아니다.

> **여기가 핵심**: 조원이 `git pull` 하는 순간 이 규칙들이 자동으로 켜진다. 아무도 각자 설정을 만질 필요가 없다.

| 종류 | 위치 | 팀 공유 |
|---|---|---|
| Project Rules | `.cursor/rules/*.mdc` (저장소 안) | 된다 — git으로 |
| User Rules | Cursor 설정 창 (내 PC) | 안 된다 — 나만 |

팀에 적용하려면 반드시 파일로 만들어 커밋해야 한다. 설정 창에 적으면 내 컴퓨터에서만 동작한다.

## 참고 — 규칙 4가지 타입

오늘은 Always와 Auto Attached 두 가지만 썼다. 네 가지 모두 같은 `.mdc` 파일이고, 파일 종류가 다른 게 아니라 **설정값만 다르다**.

| 이름 | 설정 | 언제 켜지나 | 예 |
|---|---|---|---|
| Always | `alwaysApply: true` | 무조건 매번 | 시크릿 금지, 커밋 형식 |
| Auto Attached | `globs: 경로/**` | 그 경로 건드릴 때 | 프론트 규칙, 백엔드 규칙 |
| Agent Requested | `description`만 | AI가 필요하다 판단할 때 | DB 마이그레이션 절차 |
| Manual | 셋 다 비움 | `@규칙명`으로 부를 때 | 배포 전 체크리스트 |

**고르는 법**

```
이 규칙, 모든 작업에서 지켜야 하나?
├─ 예   → Always (단, 짧게)
└─ 아니오
    ├─ 특정 폴더에서만 필요?  → Auto Attached (globs)
    ├─ 특정 상황에서만 필요?  → Agent Requested (description)
    └─ 내가 부를 때만 필요?   → Manual
```

**규칙 파일은 저절로 안 생긴다**

| 방법 | 설명 |
|---|---|
| 직접 만들기 | `.cursor/rules/이름.mdc` 파일 생성 (오늘 한 방식) |
| Cursor 메뉴 | 설정에서 New Cursor Rule |
| 채팅 명령 | `/Generate Cursor Rules` — 대화 내용으로 초안 생성 |

AI에게 "규칙 만들어줘"라고 시켜도 되지만, 만들어진 파일은 반드시 열어서 확인해야 한다 — 경로가 틀리거나, 문서를 통째로 복붙하거나, `alwaysApply`를 남발하는 경우가 많다.

### 자주 하는 실수

| 실수 | 바로잡기 |
|---|---|
| 확장자를 `.md`로 만듦 | 규칙 파일은 `.mdc` |
| 폴더명에 점을 빼먹음 (`cursor/`) | `.cursor/` — 앞에 점 |
| `---`를 빼먹음 | 설정은 `---` 두 줄 사이에 |
| 규칙에 문서를 통째로 복붙 | 짧게 쓰고 경로만 가리키기 |
| 전부 `alwaysApply: true` | 폴더 한정이면 `globs` |
| `main`에서 브랜치를 팜 | `dev`에서 파기 |
| PR을 `main`으로 올림 | `dev`로 올리기 |
| 규칙을 만들고 커밋 안 함 | 커밋해야 조원에게 적용됨 |

## 제출물 (`LAB.md`)

- 1단계 결과 스크린샷 (규칙 없이 만든 코드)
- 6단계 결과 스크린샷 (규칙 적용 후 같은 요청)
- 내가 만든 `.mdc` 파일 3개의 전문
- 7단계 실험에서 관찰한 것 (Always로 바꿨을 때 무슨 일이)
- 한 줄 정리 — "규칙을 만들고 나니 ______가 달라졌다"
- PR 링크 (대상 브랜치가 `dev`인지 확인)

**스스로 점검**

- `.mdc`와 `.md`의 차이를 설명할 수 있다
- `globs`가 무엇을 하는지 설명할 수 있다
- Always를 남발하면 안 되는 이유를 안다
- 7단계 실험 후 `alwaysApply`를 되돌렸다
- 시크릿(`.env`)이 커밋에 섞이지 않았다

## 완성 예시 — 실무용 룰셋 5종

각 룰셋은 **컨텍스트(무엇을 읽을지) + 하네스(무엇을 지킬지)** 구조다.

| 영역 | 파일 위치 | 설정 |
|---|---|---|
| 디자인 | `02/FN/.cursor/rules/design-forma.mdc` | globs |
| Git | `.cursor/rules/git-commit.mdc` | alwaysApply |
| FN 로직 | `02/FN/.cursor/rules/fn-react.mdc` | globs |
| BN | `02/BN/.cursor/rules/bn-spring.mdc` | globs |
| 인프라 | `.cursor/rules/infra-redis-db.mdc` | globs |

### Git 규칙 — 브랜치 구조

```
main              배포 기준선 (직접 커밋 금지, dev에서만 받음)
 └ dev            통합 브랜치 (직접 커밋 금지, PR로만 받음)
    ├ feature/<이름>-<요약>    기능
    ├ fix/<이름>-<요약>        버그
    ├ docs/<이름>-<요약>       문서
    └ chore/<이름>-<요약>      설정·빌드
hotfix/<이름>-<요약>           긴급 (main에서 분기)
```

| 상황 | 어디서 분기 | PR 대상 |
|---|---|---|
| 기능·버그·문서·설정 | dev | dev |
| 배포 | — | dev → main |
| 긴급 장애 | main | main + dev 양쪽 |

**dev 동기화 (merge로 통일)**

```bash
git checkout dev
git pull origin dev
git checkout feature/내브랜치
git merge dev
# 충돌 해결 후
git commit -m "merge: dev 동기화 후 <영역> 충돌 해결"
```

나머지 4종(디자인·FN·BN·인프라)의 전문은 강사님 배포 파일 참고.

## 28일 핵심 정리

---

### 1) 문서는 폴더에 있는 것만으로는 AI에게 안 보인다

```
02/FN에 상품 카드 컴포넌트 하나 만들어줘   # @ 없이 요청
```
디자인 가이드가 저장소에 있어도 AI는 그걸 읽지 않는다. 결과의 색·포맷이 사람마다 제각각인 이유 — 보여주지 않으면 AI는 모른다는 게 오늘 실습의 첫 관찰.

### 2) `@문서`로 근거를 붙이면 결과가 즉시 정확해진다 — 그러나 매번 타이핑해야 한다

```
@02/DOCS/DESIGN/2026_UIUX_디자인가이드.md 를 기준으로 ...
```
컨텍스트 엔지니어링(AI가 무엇을 보게 할지 정하는 일)의 가장 직접적인 형태. 다만 요청마다 반복 타이핑이 필요하다는 한계가 규칙 파일(`.mdc`)의 존재 이유가 된다.

### 3) 규칙은 넓은 범위 → 좁은 범위로 겹쳐 쌓는다

| 파일 | 설정 | 범위 |
|---|---|---|
| `.cursor/rules/project-rules.mdc` | `alwaysApply: true` | 전체 |
| `.cursor/rules/follow-02-docs.mdc` | `globs: 02/**` | 02 전체 |
| `02/FN/.cursor/rules/fn-design.mdc` | `globs: 02/FN/**` | 프론트 |

`02/FN` 안의 파일을 건드리면 세 규칙이 동시에 켜진다 — 전역 규칙 + 폴더 규칙 + 세부 규칙이 레이어처럼 겹치는 구조.

### 4) `globs`는 문서를 읽어오는 게 아니라 규칙을 켜는 스위치일 뿐이다

```yaml
globs: 02/**     # 이 경로를 건드리면 규칙 자체가 켜진다
```
문서를 실제로 읽게 하려면 본문에 "이 문서를 확인한다"라고 직접 적어야 한다 — 오늘 실습에서 가장 많이 헷갈린 지점.

### 5) `alwaysApply: true`를 남발하면 엉뚱한 영역에 규칙이 끼어든다

7단계 실험: FN 전용 규칙을 `alwaysApply: true`로 바꾸자 `02/BN`(Java) 작업에까지 프론트 디자인 규칙이 개입했다. `globs`로 범위를 좁혀야 하는 이유를 직접 망가뜨려서 확인한 단계 — 확인 후 반드시 원상복구.

### 6) `.cursorignore`로 민감 파일 자체를 못 보게 막는다

```
node_modules/
build/
.env
*.log
```
`.gitignore`와 같은 문법. 규칙(`.mdc`)이 "어떻게 하라"를 정한다면, `.cursorignore`는 "아예 보지 못하게" 막는 더 강한 경계선.

### 7) Project Rules는 git으로 팀 전체에, User Rules는 내 PC에만 적용된다

| 종류 | 위치 | 팀 공유 |
|---|---|---|
| Project Rules | `.cursor/rules/*.mdc` (저장소 안) | 된다 — git으로 |
| User Rules | Cursor 설정 창 (내 PC) | 안 된다 — 나만 |

오늘 만든 세 규칙 파일을 `feature/lab-내이름` → `dev` PR로 올리는 이유 — 커밋해야만 조원이 `git pull`하는 순간 자동으로 규칙이 켜진다.

### 8) 규칙에는 네 가지 타입이 있고, 오늘은 그중 둘만 썼다

| 이름 | 설정 | 언제 켜지나 |
|---|---|---|
| Always | `alwaysApply: true` | 무조건 매번 |
| Auto Attached | `globs: 경로/**` | 그 경로 건드릴 때 |
| Agent Requested | `description`만 | AI가 필요하다 판단할 때 |
| Manual | 셋 다 비움 | `@규칙명`으로 부를 때 |

오늘 실습(3~5, 8단계)은 Always와 Auto Attached만 다뤘다 — Agent Requested·Manual은 상황별·수동 호출용으로 남겨진 확장 지점.

### 9) 두 줄 정리

**컨텍스트** = AI가 보는 것을 내가 정하는 일. **하네스** = AI가 쓰는 도구와, AI가 못 하게 막는 것을 내가 정하는 일 — 하네스(harness)는 원래 말에게 채우는 마구, 힘은 그대로 쓰되 방향을 잡아주는 장치라는 뜻.
