# 7월 31일 필기 — Silver 정제 디버깅 · 리소스 최적화 · Gold 레이어

## 핵심요약

로컬 샘플 데이터로 Silver(정제) 로직을 디버깅하며 오타 버그와 self-join row 폭발 버그를 잡았다. 이어서 원본 8.4GiB 전체를 처리하다 Docker Desktop이 크래시 나는 리소스 한계를 겪었고, Bronze(Parquet 사전 변환) 도입 + executor 리소스 제한 + `repartition` 최적화로 해결했다. 마지막으로 Gold 레이어(집계 8종) 파이프라인을 완성하고, 실무에서 Bronze→Silver→Gold를 어떻게 오케스트레이션하는지 정리했다.

## 1. `02.py`(Silver 정제) 로직 디버깅

로컬(`local[*]`) 샘플 데이터로 검증하다가 발견된 문제들.

### 1-1. 실행 자체를 막는 오타/문법 버그
- `import pyspark.sql.funtions as sf` → `functions` 오타 (`ModuleNotFoundError`)
- `(df['product_id'] == mapping_df['pid'] | df['category_id'] == mapping_df['cid'])` → 괄호 누락. `==`가 `|`보다 우선순위 높아서 의도한 OR이 아니라 체인 비교로 파싱됨 → `(a == b) | (c == d)`로 괄호 필수.
- `join_condtion` 변수명 오타, `df.fillter(...)` → `filter` 오타
- `to_date(col("event_time"))` → `to_date`/`col` import 누락, `sf.to_date(sf.col(...))`로 수정
- `.withColumn(sf.col('category_code'), ...)` → `withColumn`의 1번째 인자는 문자열이어야 하는데 `Column` 객체를 넣어서 `TypeError` 발생 → `withColumn('category_code', ...)`로 수정

### 1-2. self-join 결측치 채우기 로직의 row 폭발 버그

**증상**: 샘플 10만 행을 join했더니 결과가 26,267,352행으로 폭증.

**원인**: `mapping_df`의 `.distinct()`가 `(product_id, category_id, category_code)` 조합 전체 기준이라, category_id 하나에 서로 다른 product_id가 수백 개 딸려있는 상태에서 OR 조인(`(product_id==pid) | (category_id==cid)`)을 하면 df의 한 행이 같은 category_id를 가진 mapping_df 행 전부와 매칭돼 row가 폭발함(다대다 매칭).

**해결**: 조회표를 "키 하나당 값 하나"로 만들고(`dropDuplicates(['product_id'])`, `dropDuplicates(['category_id'])`), OR 조건 하나로 합쳐 조인하지 않고 **키 컬럼 기준 순차 조인**:
```python
pid_code_map = df.filter(sf.col('category_code').isNotNull()) \
    .select('product_id', 'category_code') \
    .dropDuplicates(['product_id']) \
    .withColumnRenamed('category_code', 'code_by_pid')
# pid_brand_map, cid_map도 동일 패턴

df_join = df.join(sf.broadcast(pid_code_map), on='product_id', how='left') \
    .join(sf.broadcast(pid_brand_map), on='product_id', how='left') \
    .join(sf.broadcast(cid_map), on='category_id', how='left')

df_join = df_join.withColumn('category_code', sf.coalesce(sf.col('category_code'), sf.col('code_by_cid'), sf.col('code_by_pid'))) \
    .withColumn('brand', sf.coalesce(sf.col('brand'), sf.col('brand_by_pid')))
```
> 주의: `category_code`/`brand`를 하나의 AND 필터로 묶어서 조회표를 만들면 안 됨 — 어떤 행은 category_code만 있고 brand는 없을 수 있는데, AND로 묶으면 그 행 전체가 버려져 살릴 수 있었던 정보까지 날아감. 컬럼별로 독립된 조회표를 따로 만들어야 함.

### 1-3. 결측치 채우기 자체가 이 데이터에서는 효과 없음

검증: `df_join`에서 category_code/brand가 둘 다 채워진 행 수(59,442)가 원본 `df`에서 애초에 둘 다 있던 행 수(59,442)와 정확히 동일 — join으로 새로 채워진 행 0개.

**원인**: 이 데이터는 결측이 row 단위 랜덤이 아니라 **product_id 단위로 "카탈로그에 없는 상품은 모든 row가 항상 null"** 구조라, self-join으로 빌려올 "다른 행"이 애초에 없음. → 결측 상품은 자체 데이터로 못 채우고, 드롭하거나 외부 카탈로그를 붙여야 함.

## 2. 로컬 리소스 한계: Docker Desktop 크래시와 최적화

### 2-1. 크래시 원인
원본 전체(`2019-Nov.csv`, 8.4GiB)를 executor 리소스 제한 없이 executor 4개로 클러스터 제출했다가 Docker Desktop 자체가 응답 불능 상태가 됨. Docker Desktop VM 할당(12코어/약 8.24GB)을 3개 컨테이너가 나눠 쓰는데, 원본 파일 크기만으로 이미 가용 메모리와 맞먹어서 JVM 오버헤드/셔플 스필까지 더하면 터지는 게 당연한 상황이었음.

### 2-2. 적용한 최적화
1. **Bronze 레이어 도입**: `start.py`로 원본 CSV를 한 번 읽어 `s3a://test-bucket/bronze/cluster_mode_result`에 parquet으로 저장(8.4GiB → 2.3GiB). `02.py`는 이후 CSV 대신 bronze parquet을 읽음(CSV는 매번 `inferSchema=True`로 전체를 훑어야 해서 느림; parquet은 컬럼형+압축+스캔 불필요).
2. **executor 리소스 명시적 제한**:
```
--conf spark.driver.memory=1g
--conf spark.executor.memory=1g
--conf spark.executor.memoryOverhead=512m
--conf spark.dynamicAllocation.maxExecutors=2
```
이 설정으로 bronze 변환(27분) → silver 정제까지 크래시 없이 완주.

### 2-3. `repartition('category_code')`로 커밋 단계 최적화

`partitionBy('category_code')`로 쓸 때 원래 파티션(24개)만큼 카테고리 폴더마다 파일이 여러 개 생겨(최대 24개, 총 3014개 오브젝트) `FileOutputCommitter`가 driver 혼자 순차 커밋(S3A는 rename이 copy+delete라 더 느림)하느라 연산(4분30초)보다 커밋(14분)이 더 오래 걸림.

`write()` 직전 `.repartition('category_code')` 추가 → 같은 category_code가 반드시 같은 파티션에 모여 폴더당 파일이 정확히 1개로 줄어듦. AQE가 실제 데이터 크기(263MiB)를 보고 기본 200개 셔플 파티션을 10개까지 자동으로 줄여줘서 연산 자체도 빨라짐.

| | repartition 전 | repartition 후 |
|---|---|---|
| 전체 소요 시간 | ~20분 (커밋만 14분) | 4분 42초 |
| 오브젝트 개수 | 3014개 | 130개 |
| 폴더당 파일 개수 | 최대 24개 | 정확히 1개 |

> 주의: `repartition(col)`은 셔플 비용이 있음. `coalesce(N)`은 셔플 없이 이웃 파티션을 합치는 방식이라 싸지만 "같은 값끼리 모아준다" 보장이 없음. Gold처럼 이미 작은 집계(수십~수백 행)는 `.coalesce(1)`로 충분, `partitionBy`로 대용량을 쓸 때는 `repartition(파티션컬럼)`이 정석.

## 3. 파티션/셔플 개념 정리

- **셔플**: 여러 executor(파티션)에 흩어진 데이터를 특정 연산(dropDuplicates/groupBy/non-broadcast join/repartition/orderBy)을 위해 키 기준으로 네트워크로 재배치하는 것. `local[*]`에서도 로컬 디스크(`/tmp/spark-*`)에 임시 파일을 쓰고 읽는 방식으로 동일하게 발생함(네트워크 대신 로컬 I/O일 뿐).
- **`BroadcastExchange`는 셔플이 아님**: 작은 테이블을 통째로 모든 executor에 복사하는 것이라 큰 쪽 데이터는 이동하지 않음. `sf.broadcast()`로 명시적 유도 가능, join에서 셔플을 피하는 핵심 수단.
- **셔플 임시 데이터 저장 위치**: MinIO(S3)가 아니라 각 executor의 로컬 디스크 — job이 끝나거나 팟이 죽으면 사라짐. k3s에는 External Shuffle Service가 없어서 idle executor가 회수되면 셔플 데이터가 통째로 날아감 → `shuffleTracking.enabled=true`를 켜는 이유.
- **파티션(실행) vs `partitionBy`(저장) 구분**: Spark 실행 파티션은 메모리상 병렬 처리 단위(`df.rdd.getNumPartitions()`). `.write().partitionBy(col)`은 저장 시 컬럼 값별로 폴더를 나누는 것(폴더 개수 = 고유값 개수, 셔플/실행 파티션과 무관). **폴더 안 파일 개수 = 쓰는 시점의 실행 파티션 개수** — 이게 "small file 문제"의 근본 원인이고 `repartition(파티션컬럼)`으로 해결.

## 4. Docker Desktop 재시작 후 클러스터 복구 절차 (반복 발생 이슈)

Docker Desktop 재시작/크래시 → `k8s-master-node`(k3s) 컨테이너가 재생성되면서 k3s 내부 상태(RBAC, ServiceAccount, History Server, `spark-live-driver-ui` Service)가 전부 초기화됨. MinIO 데이터는 볼륨 마운트(`02/minio_data/`)라 생존.

**증상 확인**:
```bash
docker ps   # 컨테이너 AGE가 최근이면 재생성 의심
docker exec k8s-master-node kubectl get pods -A   # spark 관련 팟/서비스 없으면 확정
```

**복구 순서**: RBAC 재생성 → spark-events 마커 → History Server + live-driver-ui Service 재배포 → kubeconfig 재복사 → 포트포워딩 재연결.

> 주의: Windows에서 `nohup ... &`로 띄운 프로세스가 orphan으로 남아있는 채로 새로 띄우면 포트 4040 충돌. `Get-NetTCPConnection -LocalPort 4040`으로 기존 프로세스 확인 후 정리할 것.

## 5. Gold 레이어(통계) 파이프라인 (`03.py`)

Silver(`ecommerce_refined`)를 읽어 집계 결과를 `s3a://test-bucket/gold/*`에 저장. 이벤트 퍼널, 카테고리/브랜드별 매출, 일별 추이, 가격 기술통계 등 8개 테이블 생성.
```python
funnel_df = df.groupBy('event_type').count()
funnel_df.coalesce(1).write.mode('overwrite').parquet("s3a://test-bucket/gold/event_funnel")
# category_revenue, brand_revenue, daily_events, daily_purchase, price_stats 등 동일 패턴
```
각 결과가 이미 작은 집계 테이블이라 `.coalesce(1)`로 파일 1개씩 정리(셔플 없어 저비용). 실행 시간 2분 34초(silver 263MiB만 읽으면 되므로 가벼움). 결과 확인은 `resultView.ipynb`에서 `local[*]` 세션으로 `.show()`.

## 6. Bronze → Silver → Gold 파이프라인 연결 방식 (실무 참고)

- Silver+Gold를 하나의 스크립트/제출로 합치는 건 실무에서 잘 안 씀: gold 로직만 고쳐도 무거운 silver부터 매번 재실행해야 하고, 중간 실패 시 전부 재시작해야 하고, 같은 silver를 여러 gold job이 재사용하는 구조를 못 만듦.
- 실무 표준은 각 레이어를 독립 job으로 두고 오케스트레이터(Airflow `KubernetesPodOperator`, Argo Workflows, Databricks Workflows 등)로 순서/의존성만 관리. `_SUCCESS` 마커 파일이 "이전 단계가 끝났다"를 판단하는 신호로 쓰임.
- 지금은 오케스트레이터 없이 `02.py` 제출 → `_SUCCESS` 확인 → `03.py` 제출 순으로 손으로 관리 중. Airflow 학습 예정이며, 이 수동 순서가 그대로 `silver_task >> gold_task` DAG로 옮겨갈 예정.
