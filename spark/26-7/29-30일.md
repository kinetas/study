# 7월 30일 필기 — PySpark on Kubernetes(k3s) 클러스터 제출 환경 구축

## 핵심요약

오늘은 `02/` 폴더에 k3s + MinIO 기반 "가짜 프로덕션" 환경을 구축하고, `spark-submit`을 `--deploy-mode cluster`로 쿠버네티스에 제출하는 방법을 시행착오로 익혔다. 이미지 문제 → driver 이미지 미지정 → RBAC 권한 부족 → S3 자격증명/DNS 문제까지 총 7번의 시도 끝에 성공했고, 이후 동적 할당(Dynamic Allocation)과 Spark UI(4040)/History Server(18080) 상시 모니터링 체계까지 정리했다.

---

## 환경 개요

- 시작 전에 MinIO로 버킷을 먼저 만들어야 함.
- 버킷은 논리적으로 물리 저장소를 묶은 것 — 버킷에 저장해도 경로를 통해 다른 저장장치에 저장 가능.
- 버킷을 하나만 두는 경우도 있지만 여러 아키텍처가 존재하며, 메달리온 아키텍처는 브론즈/실버/골드로 나눈 구조.

## `spark-submit` 시행착오 히스토리 (시도 1~7)

### 시도 1: Jupyter 인터프리터에서 client 모드로 실행 → 실패
쿠버네티스 권한 문제 발생. RBAC로 권한 있는 역할을 만들거나, 인터프리터 대신 명령어로 cluster 형태 제출하는 방향으로 전환.

### 시도 2: `k8s-master-node`에서 `kubectl run`으로 직접 제출 → 실패
이미지(`datamechanic/spark`) 내부에 Spark 실행 바이너리가 아예 설치돼 있지 않아서 실패.
> ★ 핵심: 주피터 로컬 경로가 아닌 S3 버킷의 코드 경로를 직접 사용. 완성된 코드만 S3에 넣어서 실행(주피터 컨테이너는 설정 바꾸다 망가질 위험 있음).

### 시도 3: 공식 `apache/spark:3.4.1` 이미지로 교체 → 실패
이미지는 바뀌었지만 컨테이너 내부에서 에러 발생.

### 시도 4: ServiceAccount 지정 + ivy 경로 격리 → 실패
```
Exception in thread "main" org.apache.spark.SparkException: Must specify the driver container image
```
`--image`는 submitter 팟용일 뿐, `--deploy-mode cluster`가 새로 만드는 **driver 팟**에는 `spark.kubernetes.container.image` conf로 별도 지정 필요.

### 시도 5: driver container image 지정 → 실패
driver 이미지 문제는 해결됐지만 RBAC 에러:
```
Forbidden! User "system:serviceaccount:default:default" cannot create resource "pods"
```
Spark driver가 executor 팟을 직접 생성해야 하므로 `serviceAccountName: default`로는 권한 부족.

### 시도 6: 전용 ServiceAccount + RBAC 부여 → 부분 성공
```bash
kubectl create serviceaccount spark --namespace=default
kubectl create rolebinding spark-role --clusterrole=edit --serviceaccount=default:spark --namespace=default
```
RBAC는 해결(submitter 팟 Completed), 그러나 driver 팟이 Error:
```
NoAuthWithAWSException: No AWS Credentials provided ...
```
원인 2가지:
1. `01.py`를 driver 팟으로 내려받는 과정은 파이썬 코드 실행 **이전** 단계라서, 코드 안 `hadoop_conf.set(...)`은 소용없음 — `spark-submit --conf`로 미리 넘겨야 함.
2. `01.py`가 쓰는 `minio-storage` 호스트명은 도커 임베디드 DNS에만 등록돼 있어 k3s 팟 네트워크에서는 resolve 안 됨 → `docker inspect k8s-s3-minio`로 실제 IP(`172.19.0.3`) 확인해서 직접 사용.

### 시도 7 (최종 성공): S3A 자격증명/엔드포인트 conf 추가 + 코드 재업로드
1. `01.py`의 `fs.s3a.endpoint`를 IP(`http://172.19.0.3:9000`)로 수정 후 `code-bucket`에 재업로드
2. `spark-submit`에도 S3A 자격증명/엔드포인트를 `--conf`로 추가:
```
--conf spark.kubernetes.container.image=apache/spark:3.4.1
--conf spark.kubernetes.authenticate.driver.serviceAccountName=spark
--conf spark.jars.ivy=/tmp/.ivy
--conf spark.jars.packages=org.apache.hadoop:hadoop-aws:3.3.4,com.amazonaws:aws-java-sdk-bundle:1.12.262
--conf spark.hadoop.fs.s3a.endpoint=http://172.19.0.3:9000
--conf spark.hadoop.fs.s3a.access.key=minioadmin
--conf spark.hadoop.fs.s3a.secret.key=minioadmin
--conf spark.hadoop.fs.s3a.path.style.access=true
--conf spark.hadoop.fs.s3a.impl=org.apache.hadoop.fs.s3a.S3AFileSystem
--conf spark.hadoop.fs.s3a.connection.ssl.enabled=false
```
**결과**: 성공. driver + executor 팟 모두 Completed, `test-bucket/output/`에 `_SUCCESS` + parquet 정상 생성.

> 주의: MinIO 컨테이너 IP는 재생성 시 바뀔 수 있으므로 매번 `docker inspect`로 재확인 필요.

## Q&A 정리

### 1. 동적 할당(Dynamic Allocation)
고정 `spark.executor.instances=2` 대신:
```
spark.dynamicAllocation.enabled=true
spark.dynamicAllocation.shuffleTracking.enabled=true
spark.dynamicAllocation.minExecutors=1
spark.dynamicAllocation.maxExecutors=4
spark.dynamicAllocation.initialExecutors=1
```
`shuffleTracking.enabled=true`가 필수인 이유: k8s에는 YARN 같은 External Shuffle Service가 없어서, 이게 없으면 idle executor가 shuffle 데이터를 들고 있어도 바로 반납돼 재계산 발생.

### 2. Spark UI(4040) 접속 방법
`docker-compose.yml`에 `4040:4040`을 추가해도 소용없음 — driver는 jupyter 컨테이너가 아니라 k3s 안에 동적으로 생성되는 팟이라 컨테이너 포트 매핑과 무관. driver 실행 시 자동 생성되는 `<job>-driver-svc` 서비스를 호스트 kubectl로 port-forward해야 함.
- 단점: job이 끝나면 driver-svc가 사라지고, 매 제출마다 서비스 이름이 랜덤이라 매번 새로 찾아야 함 → 아래 "지속 모니터링 체계"로 해결.

### 3. Jupyter에서 결과 확인 (`01View.ipynb`)
`hadoop_conf.set(...)`은 SparkSession 생성 후 설정값만 바꾸는 거라 S3A jar를 classpath에 새로 못 넣음. `spark.jars.packages`는 반드시 `SparkSession.builder.config(...)`로 **세션 생성 전**에 지정해야 함. 커널이 이미 떠 있으면 Kernel → Restart 필요.

### 4. "결과 확인할 때도 쿠버네티스를 쓰나?"
`master("local[*]")`는 쿠버네티스를 전혀 안 씀 — Jupyter 컨테이너 안 JVM 하나가 로컬 코어로 driver+executor 역할을 혼자 처리. 무거운 job은 cluster 모드(kubectl run 제출), 결과 확인 같은 가벼운 작업은 로컬 모드로 정리.

### 5. 로컬 모드 vs 클러스터 모드 비교

| 구분 | 로컬 모드 | 클러스터 모드 |
|---|---|---|
| 실행 위치 | Jupyter 컨테이너 안 JVM 하나 | driver 팟 + executor 팟들 |
| 쿠버네티스 사용 | 안 함 | 씀 (팟 생성/스케줄링) |
| RBAC 필요 | 불필요 | 필요 |
| 기동 속도 | 즉시 | 느림 (이미지 pull, 스케줄링 등 30초~수 분) |
| 네트워크 이슈 | 거의 없음 | 있음 (도커 호스트명 DNS resolve 안 됨 → IP 사용) |
| 용도 | 코드 개발/디버깅, 빠른 결과 확인 | 실제 대용량 처리, 최종 검증 |

### 6. 개발 워크플로우
코드 개발/디버깅은 `local[*]`로 빠르게 반복 → 로직 완성되면 S3(code-bucket)에 올려 cluster 모드로 최종 검증. 로컬 통과가 cluster 통과를 보장하지 않음(오늘 겪은 driver 이미지/RBAC/DNS 문제는 전부 로컬에선 발생 안 하는 종류) — cluster 환경 설정은 최소 1번은 실제 제출로 확인해야 함.

## 지속 모니터링 체계 (재설정 없이 계속 보기)

### History Server (18080) — 지난 기록
기존 방식(driver-svc port-forward)의 한계: job 끝나면 서비스가 사라지고 이름이 매번 랜덤. → Spark History Server를 지속 실행 Deployment로 띄우고 event log를 MinIO(`code-bucket/spark-events`)에 남기도록 설정. 서비스 이름이 고정이라 포트포워딩을 한 번만 설정하면 이후 계속 확인 가능(단, 실시간 progress bar는 없음).

```
export SPARK_HISTORY_OPTS="-Dspark.history.fs.logDirectory=s3a://code-bucket/spark-events ..."
kubectl port-forward svc/spark-history-server 18080:18080
```

### 실시간 4040 — "지금 도는 job" 보기
`kubectl proxy` + `spark.ui.reverseProxyUrl` 조합은 실패 — Spark가 reverseProxyUrl에 "proxy"라는 단어가 들어가면 REST API 경로 파싱과 충돌해서 명시적으로 막아놓음(근본적 비호환).

**최종 해법**: Spark가 모든 driver 팟에 자동으로 붙이는 라벨 `spark-role=driver`를 셀렉터로 쓰는 고정 Service + `kubectl port-forward` 자동 재시도 루프.
```yaml
apiVersion: v1
kind: Service
metadata:
  name: spark-live-driver-ui
spec:
  selector: { spark-role: driver }
  ports: [{ port: 4040, targetPort: 4040 }]
```
```bash
# watch-4040.sh — port-forward는 팟이 죽으면 끊기므로 무한 재시도
while true; do
  kubectl port-forward svc/spark-live-driver-ui 4040:4040
  sleep 3
done
```
→ 결론: 평소엔 18080으로 지난 기록, 지금 도는지 궁금하면 4040으로 실시간 확인 — 둘 다 재설정 없이 상시 접근 가능.
