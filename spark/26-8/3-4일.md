# 8월 4일 공부 정리 — Spark 설정 우선순위 디버깅 · 레이크하우스 조회 스택(Trino/Hive Metastore/Superset) 구축

## 오늘 배운 것 요약

Spark 클러스터 job이 "executor는 정상 등록됐는데 Job/Stage가 하나도 안 생기는" 이상한 상태에 빠지는 걸 겪으면서, `spark-submit --conf`로 넘긴 설정이 코드 안의 설정으로 조용히 덮어써질 수 있다는 걸 직접 확인했다. 이 사고를 계기로 "설정값을 코드에 하드코딩하지 않고 배포 시점에 주입해야 하는 이유", "코드 배포를 왜 사람이 직접 하지 않고 CI가 대신해야 하는지"를 정리했다.

이어서 데이터 레이크(오브젝트 스토리지에 쌓인 Parquet 파일들) 위에 SQL로 바로 조회할 수 있는 실무형 쿼리 엔진 스택(Hive Metastore + Trino + Superset)을 처음부터 구축했다. 리전 설정 누락, Hadoop/AWS SDK 버전 불일치, 컨테이너 이미지에 특정 유틸리티가 빠져있어서 생긴 조용한 실패, 파이썬 패키지 의존성 충돌까지 총 4개의 문제를 순서대로 디버깅했다. 마지막으로 BI 대시보드 도구(Superset)에서 실제로 차트를 만들면서 "어떤 데이터엔 어떤 차트가 맞는지"에 대한 시각화 이론도 함께 정리했다.

## 1. "Job은 없는데 Executor는 있다" — Spark 설정 우선순위 디버깅

### 1-1. 증상

Kubernetes 위에서 `spark-submit --deploy-mode cluster`로 돌린 job의 Spark UI(포트 4040)를 열어보니, executor 2개는 정상적으로 등록되어 있는데 **Jobs/Stages 탭이 계속 비어있는** 상태가 계속됐다.

### 1-2. 원인 — Lazy Evaluation과 설정 우선순위

Spark는 lazy evaluation이라서, `.read()`나 `.filter()`처럼 transformation만 쌓는 것으로는 아무 job도 생기지 않는다. `.count()`, `.write()` 같은 **action**이 호출되는 순간에야 지금까지 쌓인 실행 계획이 실제로 돈다. 즉 "executor는 떠서 대기 중인데 job이 하나도 없다"는 건 **driver가 action을 호출하는 지점에 아직 도달하지 못하고 어딘가에서 멈춰있다**는 신호다.

원인을 코드에서 찾아보니 이런 구조였다:

```python
spark = SparkSession.builder.appName("Job").getOrCreate()

hadoop_conf = spark._jsc.hadoopConfiguration()
hadoop_conf.set("fs.s3a.endpoint", "http://<옛날 IP>:9000")   # <- 문제의 지점
...
df = spark.read.csv("s3a://bucket/data.csv", header=True, inferSchema=True)   # 여기서 멈춤
```

`hadoop_conf.set(...)`은 **SparkSession이 이미 만들어진 뒤, 코드가 실행되는 시점에** 호출되는 코드다. 그런데 spark-submit 명령에는 이미 `--conf spark.hadoop.fs.s3a.endpoint=<현재 IP>`로 올바른 값을 넘기고 있었다. 문제는 **코드 안의 `hadoop_conf.set()` 호출이 spark-submit이 넘긴 `--conf` 값을 실행 시점에 다시 덮어써버린다**는 것이었다. 그 결과 driver는 이미 죽어있는 옛날 IP로 `spark.read.csv()`를 시도하다가 응답 없이 무한 대기하고 있었던 것 — executor는 정상 등록됐지만 실제 작업 지시가 한 번도 안 내려간 상태였다.

### 1-3. 교훈 — 설정은 "누가 마지막에 쓰느냐"가 이긴다

- **설정 우선순위 규칙**: spark-submit의 `--conf`는 SparkSession을 만들 때 반영되지만, 코드 안에서 그 이후에 같은 키를 다시 `set()`하면 코드 쪽이 이긴다. "배포 시점에 주입한 설정"과 "코드에 박힌 설정"이 같은 값을 다르게 관리하고 있으면, 둘 중 하나만 고쳤을 때 반드시 이런 불일치가 생긴다.
- **해결 원칙**: 환경마다 달라지는 값(엔드포인트, 자격증명, 리소스 크기 등)은 **코드에 아예 안 적고** `--conf`나 환경변수로만 주입해야 한다. 코드 안에 있는 값을 지워버리고 외부 주입값만 쓰도록 정리하는 게 근본적인 해결책.

## 2. 왜 코드 배포를 사람이 직접 하면 안 되는가

이번 버그의 본질은 "코드가 어디에 있는지(로컬 원본 vs 실제로 실행되는 배포본)가 갈렸고, 같은 설정값이 두 군데에 중복돼서 한쪽만 고쳐졌다"는 것이었다. 실무에서 이런 사고를 막는 표준적인 방법들:

- **배포는 사람이 직접 파일을 올리는 게 아니라 CI가 자동으로 함.** git에 커밋 → CI가 테스트를 돌리고 → 통과하면 자동으로 배포. "지금 배포된 게 최신 버전인지"를 사람이 신경 쓸 필요가 없어진다.
- **고정된 파일명을 계속 덮어쓰지 않고, 버전/커밋 해시를 배포 경로에 포함시킨다.** `job.py`를 매번 덮어쓰는 대신 `jobs/v1.2.3/job.py`처럼 만들면, 문제가 생겼을 때 "이전 버전으로 롤백"이 경로 하나 바꾸는 걸로 끝난다.
- **환경별 설정(엔드포인트, 자격증명 등)은 코드에 안 박고 배포 파이프라인에서 주입한다.** 이렇게 하면 같은 코드가 개발/스테이징/운영 어디서나 재사용 가능하고, 이번 같은 "설정 중복 관리로 인한 불일치" 자체가 구조적으로 안 생긴다.

## 3. 데이터 레이크 위에 SQL 쿼리 엔진을 얹는 이유

### 3-1. Data Lake는 그 자체로 SQL 조회가 안 된다

오브젝트 스토리지(S3/MinIO 등)에 Parquet 파일을 잔뜩 쌓아뒀다고 해서 곧바로 `SELECT * FROM 테이블`을 할 수 있는 건 아니다. 파일은 그냥 파일일 뿐이고, "이 경로에 있는 파일들이 어떤 스키마를 가진 어떤 테이블이다"라는 걸 알고 있는 무언가가 따로 필요하다.

### 3-2. Schema-on-Read와 외부 테이블(External Table)

- **Schema-on-Write** (전통적 RDB): 테이블을 먼저 만들고, 그 구조에 맞는 데이터만 넣을 수 있음.
- **Schema-on-Read** (데이터 레이크/레이크하우스): 데이터는 그냥 파일로 먼저 쌓아두고, **읽는 시점에** "이걸 이런 스키마로 해석하겠다"고 사후적으로 선언함.
- 이미 존재하는 파일 더미를 가리키기만 하는 테이블을 **외부 테이블(External Table)**이라고 부른다. 메타데이터 저장소는 "위치 + 스키마" 정보만 갖고 있을 뿐, 실제 데이터 파일의 생명주기는 책임지지 않는다 — 테이블 정의를 지워도 실제 파일은 그대로 남는다.

### 3-3. 메타데이터 저장소(카탈로그)가 여러 엔진 사이의 공통 언어가 된다

Hive Metastore 같은 카탈로그의 진짜 가치는 "Spark로 쓴 테이블을 Trino로 읽고, 다른 도구로도 똑같이 인식할 수 있다"는 것이다. 서로 다른 엔진이 "테이블이 무엇인지"에 대한 합의를 카탈로그 하나로 공유하게 된다. AWS Glue Data Catalog, Iceberg/Delta의 REST 카탈로그 등도 결국 같은 역할을 하는 서로 다른 구현체일 뿐이다.

### 3-4. MPP 쿼리 엔진

Trino 같은 엔진은 **MPP(Massively Parallel Processing)** 방식으로 동작한다 — 하나의 쿼리를 여러 노드에 나눠 병렬로 처리한다는 점에서 Spark의 Driver/Executor 구조와 개념적으로 매우 비슷하다(Trino의 coordinator ≈ Spark의 driver, worker ≈ executor).

Trino와 Spark를 언제 나눠 쓰는지: Trino는 "이미 정제된 데이터를 빠르게 SQL로 조회/집계"하는 대화형 쿼리에 강하고, Spark는 "무거운 배치 변환/복잡한 파이프라인 로직"에 강하다. 그래서 보통 "Spark로 무겁게 변환 → Trino로 가볍게 서빙"하는 구조가 흔하다.

## 4. Trino + Hive Metastore + Superset 스택 구축 시행착오

실제로 로컬 Docker 환경에 이 스택(Hive Metastore, Trino, Superset)을 처음부터 구성하면서 겪은 4개의 문제. 하나같이 "설정 하나만 틀려도 조용히 실패하는" 종류라, 원인을 어떻게 좁혀갔는지가 더 중요한 부분이다.

### 4-1. Trino가 재시작 루프에 빠짐 — 리전(region) 누락

**증상**: Trino 컨테이너가 몇 초마다 계속 재시작됨.

**원인**: 로그를 확인하니 `SdkClientException: Unable to load region from any of the providers in the chain`. AWS SDK가 리전을 못 찾아서 카탈로그 로딩 자체가 실패하고 있었다. MinIO는 실제 AWS가 아니라서 리전을 자동으로 알 수 없는데, S3 호환 커넥터가 그래도 리전 값을 요구했던 것.

**해결**: 카탈로그 설정에 `s3.region=us-east-1`(MinIO는 실제로 리전을 안 쓰므로 아무 값이나 무방) 추가.

**교훈**: AWS SDK 기반 라이브러리는 실제 AWS가 아닌 S3 호환 스토리지(MinIO 등)에 붙일 때도 "리전이 있는 척"을 해줘야 하는 경우가 많다.

### 4-2. `NumberFormatException: "60s"` — Hadoop과 AWS SDK 버전 불일치

**증상**: Hive Metastore에 외부 위치를 지정해서 스키마를 만드는 요청이 `NumberFormatException: For input string: "60s"`라는 뜬금없는 에러로 실패.

**원인 파악**: 에러 메시지만 봐서는 원인을 짐작하기 어려웠다. 컨테이너 안에 실제로 내장된 Hadoop 버전을 직접 확인해보니(`hadoop-common-3.4.1.jar`), S3 접속에 필요한 보조 라이브러리(`hadoop-aws`)를 이보다 낮은 버전(3.3.6, AWS SDK v1 시절 버전)으로 잘못 넣어둔 게 원인이었다. **Hadoop 3.4.x부터는 S3 연동이 AWS SDK v1 대신 v2로 넘어갔는데**, 구버전 SDK가 클래스패스에 섞여 들어가면서 설정값을 파싱하는 방식이 꼬여버린 것이다.

**해결**: Maven 저장소에 공개된 Hadoop 프로젝트의 의존성 정의(pom.xml)에서 "이 Hadoop 버전과 정확히 짝을 이루는 AWS SDK 버전이 무엇인지"를 직접 확인한 뒤, 정확한 조합(hadoop-aws 3.4.1 + AWS SDK v2 bundle 2.24.6)으로 교체.

**교훈**: 보조 라이브러리(특히 클라우드 스토리지 연동 라이브러리)는 반드시 메인 프레임워크의 내장 버전과 **정확히** 맞춰야 한다. "저번에 다른 곳에서 됐던 조합"을 그대로 재사용하면 안 되는 이유가 여기 있다 — 이미지/배포판마다 내장 버전이 다르면 짝도 다시 맞춰야 한다.

### 4-3. 설정 파일이 조용히 반영 안 됨 — 컨테이너 이미지에 필수 유틸리티가 빠져있었음

**증상**: 위 문제를 고친 뒤에도 여전히 같은 종류의 에러(`Failed to create external path ... null`)가 발생. 메시지에 실질적인 단서가 없었음.

**원인 파악**:
1. 문제의 컨테이너 밖에서, 같은 접속 설정으로 직접 파일시스템 명령을 날려보니 **성공**함 — 이건 접속 설정 자체의 문제가 아니라 **서버 프로세스에 그 설정이 애초에 전달이 안 되고 있다**는 뜻으로 좁혀졌다.
2. 컨테이너 안에 들어가서 실제로 적용된 설정 파일이 있어야 할 자리를 직접 확인해보니 **파일 자체가 없었다**. 마운트해둔 커스텀 설정 디렉토리가 실제 설정 디렉토리로 복사/링크되는 초기화 로직이 있었는데, 그게 동작 안 하고 있던 것.
3. 컨테이너의 시작 로그를 (모든 실행 명령을 그대로 찍어주는 디버그 모드로) 처음부터 다시 확인 → `find: command not found`. 커스텀 설정 파일을 심볼릭 링크로 복사하는 초기화 스크립트가 `find` 명령을 쓰는데, 이 컨테이너 이미지(최소화된 배포판 기반)엔 `find`가 아예 없어서 그 단계가 **조용히 실패하고 넘어가고 있었다**(에러가 나도 스크립트가 멈추지 않는 방식으로 작성되어 있었음).

**해결**: 그 초기화 메커니즘을 아예 안 쓰고, 설정 파일을 최종 목적지 경로에 **직접** 마운트하도록 바꿔서 우회.

**교훈**: 컨테이너가 겉보기엔 정상적으로(재시작 루프 없이) 떠 있어도, 내부 설정이 실제로 반영이 안 됐을 수 있다. "설정을 마운트했다"와 "그 설정이 실제로 프로세스에 적용됐다"는 서로 다른 사실이고, 후자는 컨테이너 안에 직접 들어가서 확인해야만 확실하다. 이번 경우처럼 **에러를 삼키고 계속 진행하는 초기화 스크립트**는 이런 조용한 실패의 흔한 원인이다.

### 4-4. 파이썬 패키지 하나 설치했다가 애플리케이션 전체가 깨짐 — 의존성 버전 충돌

**증상**: BI 도구(Superset)에 특정 쿼리 엔진용 드라이버 패키지를 설치했더니, 정작 그 패키지는 못 찾겠다고 하고(`ModuleNotFoundError`), 이걸 고치려다가 이번엔 애플리케이션 자체가 아예 기동조차 안 되는(`ImportError`) 상태가 됐다.

**원인 파악**:
1. 처음엔 `pip install`이 애플리케이션이 실제로 쓰는 가상환경이 아니라, 권한 문제로 엉뚱한 위치(사용자 개인 설치 경로)에 조용히 폴백되어 설치되고 있었다. 그 경로를 모듈 탐색 경로에 명시적으로 추가해서 해결.
2. 그런데 그 드라이버 패키지가 설치되면서 **의존성으로 최신 버전의 핵심 라이브러리(SQLAlchemy 2.x)를 같이 끌고 왔다.** 이게 애플리케이션 코어가 이미 쓰고 있던 구버전(1.4.x)을 가려버려서, 구버전에서만 존재하던 API를 호출하는 코드가 전부 깨져버린 것.
3. 최종적으로 확인해보니, **애초에 그 별도 드라이버 패키지 자체가 필요 없었다** — 이미 설치되어 있던 상위 라이브러리(쿼리 엔진의 공식 파이썬 클라이언트)가 최신 버전에서 SQLAlchemy 다이얼렉트를 자체적으로 내장하고 있었다. 별도 드라이버 패키지는 사실상 이름만 남은 사장된 패키지였다.

**해결**: 불필요한 별도 패키지 설치를 빼고, 상위 라이브러리 하나만 설치.

**교훈**:
- 의존성을 새로 설치할 땐 "이게 기존 핵심 라이브러리의 버전을 바꿔버릴 수 있다"는 걸 항상 의식해야 한다. 특히 애플리케이션 프레임워크(웹 프레임워크, ORM 등)가 **특정 버전에 고정**되어 있는 경우, 새 패키지의 의존성이 그 버전을 몰래 올려버리면 프레임워크 코어 자체가 깨질 수 있다.
- 패키지를 설치하기 전에 "이 기능이 이미 상위 라이브러리에 내장되어 있진 않은가"부터 확인할 가치가 있다 — 라이브러리 생태계가 성숙하면서, 예전엔 별도 패키지가 필요했던 기능이 나중 버전엔 통합되는 경우가 흔하다.

## 5. 데이터 시각화 이론 — 어떤 데이터엔 어떤 차트를 써야 하는가

차트를 고르기 전에 먼저 "이 데이터로 어떤 종류의 관계를 보여주려는가"를 정하는 게 순서다. 크게 5가지로 나뉜다.

| 관계 유형 | 질문의 형태 | 대표 차트 |
|---|---|---|
| **비교(Comparison)** | 항목 간 크기를 비교 | Bar Chart |
| **추세(Trend)** | 시간에 따라 어떻게 변했나 | Line Chart, Area Chart |
| **구성(Composition)** | 전체 중 각 부분의 비중 | Stacked Bar, (제한적으로) Pie |
| **분포(Distribution)** | 값들이 어떻게 퍼져있나 | Histogram, Box Plot |
| **관계(Relationship)** | 두 변수가 서로 연관 있나 | Scatter Plot |

### 5-1. 비교 — Bar Chart

- 범주형 축(카테고리, 브랜드 등) + 숫자 지표(매출, 개수 등) 조합엔 Bar Chart가 기본값.
- **정렬이 핵심**: 값 기준으로 내림차순 정렬 안 하면 눈으로 비교하기 어렵다.
- **Top N 처리**: 카테고리 종류가 많으면 전부 보여주지 말고 상위 N개만 + "기타"로 묶는 게 가독성이 좋다.

### 5-2. 추세 — Line/Area Chart

- 시간(날짜/시각) 축이 있는 데이터는 거의 항상 Line Chart.
- Line vs Area: 값 자체의 변화 패턴이 궁금하면 Line, "크기감"(누적된 양의 느낌)까지 보여주고 싶으면 Area — 단 여러 계열을 Area로 겹치면 오히려 안 보일 수 있어서 계열이 2~3개 이하일 때 추천.

### 5-3. 구성 — Pie/Donut의 함정

- Pie/Donut 차트는 "전체 대비 비중"을 보여주지만, **실무에서는 의외로 지양되는 경우가 많다.** 사람 눈은 각도/면적보다 길이(막대)를 비교하는 데 훨씬 정확하기 때문 — 조각이 3~4개를 넘어가면 크기 차이를 거의 구분 못 한다.
- 대안: 비중 비교가 목적이면 정렬된 Bar Chart(또는 100% Stacked Bar)가 대부분 더 명확하다. Pie는 "정확히 2~3개 항목의, 차이가 뚜렷한 비중"을 보여줄 때만 제한적으로 유효하다.
- "단계별로 줄어드는" 데이터(예: 방문→장바구니→구매 같은 전환 흐름)는 Pie가 아니라 **Funnel Chart**(퍼널 전용, 이탈률 시각화에 특화)가 정확히 맞는 형태다.

### 5-4. 분포 — Histogram/Box Plot/Table

- 값들이 어떻게 퍼져 있는지(평균, 중앙값, 이상치 등)가 궁금하면 분포 전용 차트가 필요하다.
- 이미 count/mean/stddev/min/max 같은 요약 통계로 집계가 끝난 데이터는, 굳이 다시 차트로 그리기보다 **Table**로 그대로 보여주는 게 오히려 명확할 때가 많다(숫자 몇 개뿐이라 시각화의 이점이 적음).
- 사분위수(p25/median/p75/p95)처럼 항목이 몇 개 안 되는 요약값은 Bar Chart로 구간별 값을 비교하기 좋다. 반면 원본 개별 값 전체가 있다면 Histogram이나 Box Plot이 더 적합하다.

### 5-5. 관계 — Scatter Plot

- 두 숫자 변수 사이에 상관관계가 있는지 볼 때 사용. 예: "가격이 높을수록 구매전환율이 낮은가" 같은 질문에 매출/구매건수 같은 두 지표를 x/y로 놓으면, "매출은 높은데 구매건수는 적은(=객단가가 높은) 항목"을 찾는 식으로 활용할 수 있다.

### 5-6. 흔한 실수 — 오해를 부르는 시각화

- **Y축을 0부터 시작하지 않는 Bar Chart**: 막대 높이 차이가 실제 값 차이보다 과장되어 보인다 — Bar Chart는 반드시 0부터 시작해야 한다(Line Chart는 추세만 보여주는 목적이면 예외적으로 허용되기도 함).
- **범례가 너무 많은 색상 구분**: 계열이 7~8개를 넘어가면 색으로 구분이 사실상 불가능하다 — Top N + 기타로 줄이거나 여러 개의 작은 차트로 나누는 게 낫다.
- **단일 숫자(Big Number) 카드 남용**: KPI 하나를 강조할 땐 좋지만, 맥락(전 기간 대비 증감 등) 없이 숫자만 던지면 "그래서 좋은 건지 나쁜 건지" 판단이 안 된다.
- **차트 종류보다 먼저 확인할 것**: "이 숫자가 합계(SUM)인지 평균(AVG)인지 개수(COUNT)인지"부터 명확히 해야 한다 — 집계 함수를 잘못 고르면 차트 모양이 멀쩡해도 숫자 자체가 틀린다.

## 6. BI 도구에서 대시보드 만드는 일반적인 흐름

오늘 실제로 Superset(오픈소스 BI 도구)에서 대시보드를 만들며 확인한, 대부분의 셀프서비스 BI 도구에 공통적으로 적용되는 흐름:

```
데이터베이스 연결
   ↓
데이터셋(Dataset)         테이블 하나 = 데이터셋 하나, 또는 SQL 쿼리 결과를 데이터셋으로 저장
   ↓
차트(Chart)               데이터셋 + 어떤 컬럼을 축/지표로 쓸지 + 차트 종류
   ↓
대시보드(Dashboard)        차트 여러 개를 한 화면에 배치, 필터를 여러 차트에 동시 적용 가능
```

- 데이터셋을 만드는 방법은 보통 두 가지다: (1) SQL 편집기에서 쿼리를 짜보면서 결과를 데이터셋으로 저장하는 방식(탐색하면서 만들 때 유리), (2) 테이블 목록에서 바로 선택해서 만드는 방식(이미 어떤 테이블이 필요한지 알 때 빠름).
- 차트를 만들 땐 **지표(Metric, 보통 숫자 컬럼을 SUM/COUNT/AVG 등으로 집계)**와 **차원(Dimension, 범주형 컬럼, 막대/선을 나누는 기준)**을 지정하는 게 핵심이다.
- 대시보드에서 여러 차트가 같은 컬럼(예: 날짜, 카테고리)을 공유하고 있으면, 대시보드 레벨 필터 하나로 모든 차트에 동시에 적용할 수 있다 — 개별 차트마다 필터를 따로 설정할 필요가 없다.
